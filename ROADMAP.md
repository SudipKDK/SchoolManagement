# School Management Platform — Roadmap

Modular monolith: Express 5 + TypeScript + Prisma 7 + PostgreSQL + Redis, Next.js frontend. Multi-tenant (shared schema, `schoolId` derived from the authenticated user, never from the client).

## 1. Where the project is today

Done (backend):
- Foundation: config/env, Prisma + pg adapter, error handler, Zod `validate` middleware, Docker compose (Postgres, Redis).
- Auth: login, refresh tokens, JWT utils, with unit tests.
- RBAC: `Role`, `RolePermission`, `UserRole`, permission catalog, `authorize()` middleware, RBAC seeding.
- Tenancy: `requireAuth` -> `requireSchool` -> `authorize` chain.
- School and member modules (add users to a school).
- Academic module: academic years, terms, classrooms, subjects, teacher-subject-class assignment, timetable periods (with unit tests).
- Student CRUD and teacher profile (partial).

Not started: the whole frontend (`frontend/app` is the create-next-app default), guardians, enrollment, attendance, exams, fees, notifications, audit, documents, workers, CI, API docs.

## 2. Why it feels stuck: gaps to fix first

These are design debts that every later module will build on. Fix them before adding attendance.

1. `Student.classroomId` puts the class directly on the student. Replace with `Enrollment` (student + academicYear + grade + section + status). Otherwise promotions lose history.
2. `Classroom` mixes Grade and Section ("Grade 10-A"). Split into `Grade` and `Section` (Section belongs to Grade + AcademicYear, with class teacher).
3. `Student` has no linked `User`, no admission number, no status (ACTIVE/INACTIVE/GRADUATED/TRANSFERRED), no guardians. Add `userId?`, `admissionNumber` (unique per school), `status`, gender, etc. Use soft status, not deletes.
4. Add `Guardian` and `StudentGuardian` (relationship, isPrimary, isEmergencyContact) plus a PARENT role.
5. `ClassSubject` (grade/section + subject + teacher) should replace the current `TeacherSubjectClass` semantics; timetable periods should reference it.
6. Timetable times are strings and uniqueness only covers identical start times. Introduce `Period` (school-defined slots) and `Room`, and do real overlap detection in the service.
7. No `AuditLog` table, no domain-event layer. Add both now: they are cheap early and painful later.
8. Roles are school-scoped through `UserRole.schoolId` but `@@unique([userId, roleId])` blocks one user holding the same role in two schools. Make it `[userId, roleId, schoolId]`.
9. Working tree has a large uncommitted change set. Commit it in logical chunks (schema, auth, academic, tests) after step 3 below, and add `backend/src/generated` to `.gitignore` if it is regenerated by `prisma generate`.
10. Student/teacher/member modules have no tests and the student module has no permission seed alignment with the new catalog. Add tests as each module is reworked.

## 3. Roadmap

Each phase ends with a demo-able milestone. Estimates assume one developer, part time.

### Phase A — Stabilise the core (1–2 weeks)
- Commit current work; run `typecheck`, `test`, `lint`; get all green.
- Prisma migration: Grade, Section, Enrollment, Guardian, StudentGuardian, Room, Period, ClassSubject, AuditLog; Student changes; UserRole unique fix. Write a data migration for any dev data, or reset dev DB.
- Rework student, classroom (-> grade/section) and teacher modules to the new model.
- Create-student transaction: user (optional) + student + enrollment + guardian links.
- Audit log service called from services on create/update/delete of sensitive entities.
- Add `GET /api/v1/health`, request ID + pino logging, standard response envelope, OpenAPI docs (zod-to-openapi or similar).
- Add integration tests against a test database (docker Postgres), including tenant-isolation tests (school A cannot read school B).

Milestone 1 (your original target): admin creates academic year -> grade 8 -> section A -> teacher -> student -> enrolls student; teacher logs in and sees section 8A.

### Phase B — Frontend shell (2 weeks)
Read `frontend/AGENTS.md` and `node_modules/next/dist/docs/` first: this Next.js version differs from what is commonly known.
- API client with typed responses, auth (access token in memory, refresh via httpOnly cookie), route guards by role/permission.
- Layout with role-based navigation; login page.
- Admin screens: school setup wizard (year, terms, grades, sections, subjects), teachers list/create, students list/create/enroll, guardians.
- Teacher home: "today's classes" from the timetable.

Milestone 2: Milestone 1 performed entirely through the UI.

### Phase C — Attendance (1–2 weeks)
- `AttendanceSession` (section + date + period/day) and `AttendanceRecord` (PRESENT/ABSENT/LATE/EXCUSED/HALF_DAY), unique per student per session.
- Teacher marks and submits, record locks; `AttendanceCorrection` with reason and audit entry; ABAC rule: teacher only for their sections.
- Reports: daily, monthly, per student, per section. Admin dashboard counts.
- Emit `AttendanceMarked` / `StudentAbsent` domain events (handlers initially log and audit).

Milestone 3: teacher marks attendance in the UI, admin sees today's absentees.

### Phase D — Event system, queue, notifications (1–2 weeks)
- In-process event bus with handlers, then BullMQ workers (Redis already in compose) in a separate `worker` entry point.
- `Notification` model + `NotificationService` with channels: in-app first, then email; SMS/push later behind the same interface.
- Parent notification on absence. Guardian notification preferences.
- Announcements (school, grade, section audiences), read/unread.

Milestone 4: marking a student absent notifies the guardian in-app and by email.

### Phase E — Timetable proper (1 week)
- Periods, rooms, conflict engine (teacher, room, section overlap), clone timetable between terms.
- Teacher and section views, "today's timetable" endpoints feeding dashboards.

### Phase F — Exams and grades (2–3 weeks)
- `GradingScale` (configurable bands), `Exam` (term, type), `ExamSubject` (max/pass marks, weight), `ExamResult`/`ExamResultItem`.
- Mark entry limited to assigned teacher/subject/section, publish step (locks marks, emits `ExamResultPublished`), grade changes audited with old/new value.
- Term aggregates and ranking; unit tests for grade calculation.
- Report cards: PDF generated by a queue worker, stored in object storage, guardian notified.
- Assignments/homework (create, submit, grade) can be a sub-phase here.

Milestone 5: teacher enters marks, admin publishes, parent downloads a report card.

### Phase G — Parent and student portals (1–2 weeks)
- Parent dashboard with child switcher: timetable, attendance, results, announcements.
- Student dashboard. Permissions scoped to "own children" / "self".
- Student 360 view for admin and teachers.

### Phase H — Finance (3 weeks)
- FeeCategory, FeeStructure (per grade/year), Invoice + InvoiceItem, Payment, Discount/Scholarship, Refund, Adjustment. Balances are computed from ledger rows, never stored.
- Bulk invoice generation as a job; receipts as PDF.
- Payment gateway for your market with server-side webhook verification, idempotency keys.
- Reports: collection, outstanding, per student.

### Phase I — Documents (1 week)
- S3-compatible storage (MinIO in dev), signed URLs, `Document` table, access control by owner/role. Student documents, certificates, receipts, report cards.

### Phase J — Reports and analytics (1–2 weeks)
- Attendance, academic and finance reports, CSV export as jobs, admin KPI dashboard. Add DB indexes from observed queries.

### Phase K — Hardening and release (2 weeks, start CI earlier)
- GitHub Actions: install, lint, typecheck, unit + integration tests, build, Docker image.
- Dockerfiles for api, worker, frontend; staging and production environments; env validation; secrets from environment only.
- Rate limiting on auth routes, secure headers (helmet already present), refresh token rotation and revocation, login history, password reset and email verification.
- Backups, monitoring (request IDs, error tracking, queue metrics).
- Security review and load test of the main flows.

### Phase L — Later modules (as needed)
Library, transport, inventory, HR/leave/payroll, events, discipline, emergency/medical info, bulk import (CSV), search (OpenSearch only if Postgres becomes insufficient), early-warning indicators, AI assistant (must go through the same authorization layer).

## 4. MVP cut line
Phases A, B, C, D (announcements + absence notification), F, G. Finance (H) is the first post-MVP release. Phases I–K can overlap with the others, but CI should start in Phase A.

## 6. Working rules
- Business logic in services, thin controllers, repositories own Prisma calls; every query filters by `schoolId`.
- Every new module: schema -> validator -> repository -> service (+unit tests) -> controller/route with `authorize()` -> permission added to the catalog and seed.
- No hard deletes for people, finance, or audit data.
- One phase at a time; do not start the next until the milestone demo works.
